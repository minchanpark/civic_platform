| 제품 범위 | 타오위안 환경미화 중심 민원 접수·처리·현장 재발 확인·집계형 플레이어 |
| 장기 방향 | 타오위안시 24시간 공식 민원 접수 및 현장 해결 확인 서비스 |

## 1. 제품 요약

CivicPin은 시민이 타오위안 지도에 환경 관련 문제의 위치를 PIN으로 표시하고 제목, 본문과 사진을 제출한 뒤 티켓 번호로 처리 현황을 확인하는 민원 플랫폼이다. 관리자는 지도와 전체 목록에서 민원을 확인하고, 열람·처리·보류·완료 상태를 변경한다.

CivicPin은 행정 처리가 끝났다는 사실과 현장에서 문제가 실제로 해결됐다는 사실을 분리한다. 관리자가 민원을 완료해도 해당 문제지점의 현장 상태는 자동으로 해결되지 않는다. 같은 위치에서 새 사진 신고가 접수되면 서버가 과거 완료 민원과 비공개로 연결하고, 검증된 재발이 누적되면 관리자에게 해결이 시급한 문제지점으로 표시한다.

개별 민원은 시민 간 또는 공개 플레이어에 공개하지 않는다. 공개 플레이어는 13개 행정구의 충분히 집계된 통계와 익명 문제지점만 보여준다. 원본 제목, 본문, 사진, 티켓 번호, 신고자 정보, 정확한 PIN과 실시간 접수 시각은 시민 본인과 권한 있는 관리자만 볼 수 있다.

이번 제품은 환경미화 관련 세 카테고리부터 시작한다. 기존 행정 시스템 연동, 법정 보존기간과 공식 SLA는 별도 승인 전까지 범위에 포함하지 않으며, 공식 민원 채널로 표시하지 않는다.

## 2. 확정된 제품 결정

- **D-001** CivicPin이 티켓, 행정 상태, 상태 이력, 문제지점, 현장 상태와 재발 연결의 정본이다.
- **D-002** 시민은 제출 전에 이메일 OTP를 확인한다. 검증된 사용자 ID가 티켓 소유권이며 티켓 번호는 조회 권한이 아니다.
- **D-003** 초기 카테고리는 `도로·보도`, `쓰레기·환경오염`, `공원·공공시설` 세 개로 고정한다.
- **D-004** 행정 상태와 현장 상태를 서로 다른 상태 모델과 이벤트 이력으로 관리한다.
- **D-005** 관리자의 행정 완료는 현장 해결을 자동으로 의미하지 않는다.
- **D-006** 재발 신고는 완료된 원본 티켓을 다시 열지 않고 새 티켓으로 생성해 같은 문제지점에 연결한다.
- **D-007** 시민은 다른 시민의 개별 민원과 정확한 PIN을 조회하지 않는다. 서버가 위치·카테고리·시각을 이용해 관련 민원을 비공개로 연결한다.
- **D-008** 공개 플레이어는 개별 민원이 아닌 행정구 통계와 공개 기준을 충족한 익명 문제지점만 보여준다.
- **D-009** 시민 제출 사진, 재발 증빙 사진과 처리 후 사진은 공개 플레이어에 표시하지 않는다.
- **D-010** 위험도 1~5단계는 AI가 이유와 함께 제안하고 관리자가 처음부터 수정할 수 있다. AI는 민원을 거부·보류·완료·공개할 수 없다.
- **D-011** `completed`는 관리자의 최종 답변과 명시적 확인으로만 설정한다.
- **D-012** 관리자 번호는 개인별 식별자이며 단독 인증수단이 아니다. 활성 멤버십, 이메일 OTP와 세션별 관리자 번호 확인을 함께 사용한다.
- **D-013** 시민·플레이어의 초기 지원 언어는 번체 중국어, 영어, 베트남어이며 번체 중국어가 기본이다.
- **D-014** 공개 통계는 최대 5분 간격의 서버 집계 snapshot으로 갱신하며 원본 민원을 직접 공개하지 않는다.

## 3. 목표와 성공 기준

### G-01. 좁고 명확한 환경 민원 접수

시민이 `카테고리 → 지도 확인 → PIN → 제목·본문·사진 → 이메일 확인 → 제출 → 티켓 확인`을 모바일에서 완료할 수 있어야 한다.

### G-02. 이해 가능한 행정 진행

시민이 자기 티켓의 `접수됨`, `담당자 확인 중`, `현장 처리 중`, `보류`, `완료` 상태와 각 변경 시각, 보류 사유, 다음 확인 예정일과 완료 답변을 볼 수 있어야 한다.

### G-03. 행정 완료와 현장 해결의 분리

관리자 완료 후에도 문제지점의 현장 상태를 `확인 필요`로 유지하고, 처리 후 증빙이나 재발 신고를 통해 `해결 확인` 또는 `재발 확인`으로 갱신해야 한다.

### G-04. 재발 기반 문제지점 발견

서로 다른 시민의 검증된 재발이 반복되는 위치를 하나의 문제지점으로 묶고, 관리자 지도와 목록에서 재발 횟수와 시급성을 확인할 수 있어야 한다.

### G-05. 지도 중심 관리자 처리

관리자가 첫 화면의 지도에서 모든 개별 민원 PIN을 확인하고, PIN 하단 시트 또는 전체 목록의 동일한 상세 화면에서 열람·처리·보류·완료 작업을 수행할 수 있어야 한다.

### G-06. 개인정보를 노출하지 않는 공공 현황판

플레이어는 개별 민원 없이 13개 행정구의 환경 민원량, 행정 처리율, 현장 해결 확인율과 충분히 집계된 문제지점만 보여줘야 한다.

### G-07. 실제 다기기 연결

시민 제출, 관리자 상태 변경, 재발 연결, 이메일과 집계 snapshot이 정적 데모가 아닌 실제 서버 데이터로 연결되어야 한다.

## 4. 사용자와 화면

### 4.1 시민

- 회원가입 화면이나 비밀번호 없이 이메일로 본인을 확인한다. 접수 화면은 OTP를, 내 티켓 조회 화면은 일회용 매직 링크를 사용한다.
- 자기 티켓, 상태 이력, 완료 답변과 자기 티켓에 연결된 사진만 본다.
- 다른 시민의 개별 민원, 사진, 티켓 번호와 정확한 위치를 볼 수 없다.
- 일반 신고 또는 현재 위치와 앱 카메라를 이용한 재발 증빙 신고를 제출한다.
- 행정 상태나 AI 위험도, 문제지점 연결을 직접 수정할 수 없다.

### 4.2 관리자

- 개인별 관리자 번호, 활성 관리자 멤버십과 이메일 OTP를 모두 통과해야 한다.
- 정확한 PIN, 시민 작성 내용, 연락처, 비공개 사진과 내부 AI 결과를 업무상 필요한 범위에서 본다.
- 지도 하단 시트와 전체 목록 상세 모달에서 같은 명령과 최신 데이터를 사용한다.
- 상태 변경, 부서 전달, 위험도 수정, 재발 연결 승인, 처리 후 증빙 등록과 완료 확인을 수행한다.

### 4.3 공개 플레이어 시청자

- 로그인 없이 행정구 단위 통계와 공개 기준을 충족한 익명 문제지점만 본다.
- 개별 티켓, 제목, 본문, 사진, 신고자, 관리자 메모, 정확한 좌표와 실시간 이벤트를 받지 않는다.
- 자동 순환을 일시정지·재개하고 키보드로 지역과 집계 항목을 탐색할 수 있다.

### 4.4 시민 메인 화면

- 환경미화 세 카테고리 선택 메뉴
- `새 민원 접수`와 `내 티켓 확인` 진입
- 스크롤 아래의 내 민원 행정 상태별 현황
- 로그인 전에는 개인정보 없는 행정구 집계 요약
- 로그인 후에는 자기 티켓 목록과 최근 변경 시각
- 공개 기준을 충족한 경우에만 내 주변 500m의 익명 문제지점 요약

### 4.5 관리자 메인 화면

- 모든 개별 민원 PIN과 문제지점을 표시하는 지도
- 지도 상단의 `미열람`, `열람`, `진행 중`, `보류`, `완료` 건수
- 상태·카테고리·행정구·위험도·재발 여부 필터
- PIN 선택 시 올라오는 상세 하단 시트
- 전체 민원 목록 진입

### 4.6 관리자 전체 목록

- 최신순, 위험도순, 재발순 정렬
- 지도와 같은 필터
- 민원 클릭 시 지도 하단 시트와 같은 상세 컴포넌트를 모달로 표시
- 목록과 지도 사이에서 선택 상태를 유지

## 5. 상태와 핵심 개념

### 5.1 행정 상태

```text
received → viewed → in_progress → completed
                 ↘ on_hold ↗
        in_progress ↔ on_hold
```

| 내부값 | 관리자 표시 | 시민 표시 | 설정 조건 |
|---|---|---|---|
| `received` | 미열람 | 접수됨 | 사진과 티켓, 최초 이벤트가 모두 저장됨 |
| `viewed` | 열람 | 담당자 확인 중 | 권한 있는 관리자가 상세를 최초로 성공적으로 열음 |
| `in_progress` | 진행 중 | 현장 처리 중 | 명시적 처리 시작, 저장된 AI 작업 또는 부서 전달 중 하나가 성공함 |
| `on_hold` | 보류 | 보류 | 관리자가 사유와 다음 확인 예정일을 저장함 |
| `completed` | 완료 | 완료 | 관리자가 최종 답변을 입력하고 명시적으로 확인함 |

행정 상태 규칙은 다음과 같다.

- 지도 렌더링, 목록 표시, hover와 링크 미리읽기는 `viewed`가 아니다.
- `received → viewed`는 최초 한 번만 원자적으로 기록한다.
- `on_hold`는 `viewed` 또는 `in_progress`에서 진입할 수 있고 `in_progress`로만 복귀한다.
- `on_hold`에서 바로 `completed`로 이동할 수 없다.
- `completed`는 MVP에서 되돌리지 않는다. 후속 조치가 필요하면 새 티켓을 연결한다.
- 모든 상태 변경은 현재 상태 갱신과 append-only 이벤트 추가를 같은 트랜잭션에서 처리한다.

### 5.2 문제지점과 현장 상태

문제지점은 같은 행정구·카테고리에서 PIN 반경 30m 안의 티켓을 비공개로 묶는 내부 단위다. 유효한 연결 민원이 5건 이상이면 관리자 지도에서 개별 PIN을 하나의 문제지점 마커로 표시하고 문제지점 필터와 연결 건수를 제공한다. 각 티켓의 행정 이력은 그대로 유지하며 문제지점에는 별도의 현장 상태 이력이 있다.

```text
active → verification_pending → resolved_confirmed
  ↑              ↘                    ↘
  └──────── recurrence_confirmed ←─────┘
```

| 내부값 | 표시 | 의미 |
|---|---|---|
| `active` | 현장 문제 있음 | 처리되지 않은 연결 티켓이 있음 |
| `verification_pending` | 현장 확인 필요 | 연결 티켓은 행정 완료됐지만 해결 증빙이 충분하지 않음 |
| `resolved_confirmed` | 해결 확인 | 허용된 처리 후 증빙으로 현장 해결이 확인됨 |
| `recurrence_confirmed` | 재발 확인 | 완료 또는 해결 확인 뒤 같은 문제가 다시 검증됨 |

- 행정 완료만으로 `resolved_confirmed`가 되지 않는다.
- 처리 후 현장 사진과 점검 기록이 없으면 `verification_pending`을 유지한다.
- 관리자가 등록한 처리 후 사진과 점검 기록으로 해결을 확인한다.
- 시간이 지났거나 신고가 없다는 이유만으로 해결 확인으로 자동 전환하지 않는다.
- 재발 확인 시 과거 티켓은 완료 상태로 보존하고 새 티켓을 `received`로 생성한다.

### 5.3 재발과 시급 문제지점

- 시민이 일반 신고를 제출하면 서버는 같은 카테고리, 반경 30m와 최근 90일의 완료 문제지점을 검색한다.
- 일치 결과는 시민에게 원본 민원을 노출하지 않고 `재발 후보`로만 내부 저장한다.
- 앱 카메라 촬영, 촬영 후 5분 이내 제출, 현재 위치가 신고 PIN 반경 500m 이내인 사진은 `현장 증빙 가능`으로 표시한다.
- 브라우저나 기기가 실시간 카메라·위치 확인을 지원하지 않으면 일반 신고는 가능하지만 자동으로 검증된 재발에 포함하지 않는다.
- 서버는 위치·카테고리·기간 규칙으로 재발 후보와 이유를 만들고, 관리자가 사진을 확인해 최종 연결을 승인하거나 해제한다.
- 한 사용자가 같은 문제지점에 24시간 내 반복 제출한 건은 시급성 집계에서 하나로 센다. 원본 티켓은 보존한다.
- 최근 90일, 반경 30m 안에서 서로 다른 시민 2명 이상의 검증된 재발 3건이 쌓이면 관리자용 `시급 문제지점`으로 표시한다.
- 문제지점 표시는 관리자 우선순위에 영향을 주지만 행정 상태나 AI 위험도를 자동 변경하지 않는다.

### 5.4 AI 위험도

| 단계 | 표시 | 예시 기준 |
|---|---|---|
| 1 | 낮음 | 경미한 미관 문제, 즉시 위해 없음 |
| 2 | 보통 | 일반 청소·정비가 필요한 문제 |
| 3 | 주의 | 보행 방해, 반복 오염, 이용 불편 확대 |
| 4 | 높음 | 사고·건강 위험 또는 빠르게 확산되는 오염 |
| 5 | 긴급 | 즉각적인 인명 위험 또는 대규모 환경 위해 가능성 |

- AI는 위험 단계, 이유 코드와 판단 근거가 된 입력 범위를 함께 저장한다.
- 관리자는 첫 버전부터 위험도를 수정할 수 있으며 변경 이유를 남긴다.
- 긴급 위험 가능성은 관리자에게 강조하지만 CivicPin이 긴급 신고 채널을 대신하지 않는다.
- AI 실패 시 기본 위험도를 조작하지 않고 `평가 필요`로 남긴다.
- AI 위험도는 자동 거부, 자동 공개, 자동 부서 전달, 자동 보류 또는 자동 완료를 실행하지 않는다.

## 6. 핵심 사용자 여정

### J-01. 시민 신규 민원 접수

1. 시민이 `도로·보도`, `쓰레기·환경오염`, `공원·공공시설` 중 하나를 선택한다.
2. 고정 URL에서는 행정구를 선택하고, 지역 QR에서는 행정구가 초안에 고정된다.
3. 시민이 지도에서 위치를 선택해 PIN 하나를 놓는다.
4. 시민이 제목, 본문과 현장 사진 한 장을 입력한다.
5. 개인정보·사진·AI 처리 안내를 확인한다.
6. 이메일 OTP를 완료한다.
7. 위치와 내용을 최종 확인하고 제출한다.
8. 서버가 인증, 입력, 좌표, 사진, 빈도와 중복 요청을 검증한다.
9. 티켓, 비공개 연락처·사진, 최초 `received` 이벤트와 문제지점 후보를 저장한다.
10. 시민에게 티켓 번호, 접수 시각과 인증이 필요한 조회 경로를 보여준다.

### J-02. 시민 상태 확인

1. 시민이 제출에 사용한 이메일로 일회용 매직 링크를 받아 내 티켓을 연다.
2. 전체 또는 `접수됨`, `담당자 확인 중`, `현장 처리 중`, `보류`, `완료` 탭으로 자기 티켓을 나눠 본다.
3. 개별 티켓에서 현재 행정 상태와 상태별 변경 시각을 본다.
4. 보류 상태에서는 사유와 다음 확인 예정일을 본다.
5. 완료 상태에서는 관리자의 최종 답변과 문제지점의 현장 상태를 본다.
6. 열린 화면은 변경 신호를 받은 뒤 권한에 맞는 최신 snapshot을 다시 조회한다.

### J-03. 시민 재발 증빙 신고

1. 시민은 자기 티켓 중 행정 완료됐지만 현장 해결이 확정되지 않은 티켓에서 재신고를 시작한다.
2. 앱이 현재 위치 권한을 요청하고, 서버는 로그인 사용자와 원본 티켓 소유권·완료 상태·현장 상태를 확인한 뒤 현재 위치가 원본 PIN 반경 500m 안인지 검증한다.
3. 위치가 승인된 경우에만 앱 내부 카메라를 열고 서버가 5분짜리 1회 제출 토큰을 발급한다.
4. 시민은 카메라 화면에서 사진을 새로 촬영한 뒤 제목과 설명을 입력하고 5분 이내 제출한다.
5. 서버는 토큰, 원본 티켓, 제출 시각, 사진 형식과 중복 요청을 다시 검증하고 원본 카테고리·행정구·PIN에 새 티켓을 연결한다.
6. 관리자 또는 승인 규칙이 재발을 확인하면 문제지점을 `recurrence_confirmed`로 변경한다.
7. 시민에게는 새 티켓만 보여주고 다른 신고자의 원본 민원은 보여주지 않는다.

### J-04. 관리자 처리

1. 관리자가 이메일 OTP를 완료하고 개인 관리자 번호를 입력한다.
2. 관리자 지도는 모든 개별 PIN, 행정 상태와 시급 문제지점을 표시한다.
3. 관리자가 PIN을 선택하면 하단 시트가 열리고 최초 한 번만 `received → viewed`가 기록된다.
4. 관리자는 본문, 비공개 사진, 연락처, AI 위험도와 재발 후보를 확인한다.
5. 처리 시작, 저장된 AI 작업 또는 부서 전달이 성공하면 `in_progress`로 변경한다.
6. 보류가 필요하면 사유와 다음 확인 예정일을 저장한다.
7. 완료 시 최종 답변을 입력하고 선택적으로 처리 후 현장 사진을 등록한 뒤 최종 확인한다.
8. `completed` 이벤트와 완료 이메일 작업을 같은 트랜잭션에 기록한다.
9. 처리 후 증빙이 충분하면 현장 상태를 `resolved_confirmed`, 아니면 `verification_pending`으로 둔다.

### J-05. 관리자 전체 목록

1. 관리자가 지도에서 전체 목록으로 이동한다.
2. 상태, 카테고리, 행정구, 위험도와 재발 여부로 필터링한다.
3. 최신순, 위험도순 또는 재발순으로 정렬한다.
4. 민원을 선택하면 지도와 동일한 상세 UI가 모달로 열린다.
5. 모달에서 수행한 변경은 지도, 목록과 시민 화면에 동일하게 반영된다.

### J-06. 13개 행정구 공개 플레이어

1. 플레이어가 타오위안 13개 행정구를 자동 순환한다.
2. 축소 화면은 여러 행정구의 민원량과 집계 클러스터를 동시에 보여준다.
3. 행정구 확대 화면은 개별 민원 대신 카테고리별 밀도와 공개 기준을 충족한 익명 문제지점을 보여준다.
4. 플레이어는 최근 90일의 행정 처리율과 현장 해결 확인율을 별도로 보여준다.
5. QR은 현재 행정구가 고정된 신규 신고 화면으로 연결한다.
6. 모든 데이터는 최대 5분 간격의 공개 집계 snapshot을 사용하며 자동 순환은 일시정지·재개할 수 있다.

## 7. 기능 요구사항

### 7.0 화면 경로

- **FR-RT-001** `/`는 시민 서비스의 시작 화면이고 `/admin`은 관리자 인증·업무 화면이다. 두 경로는 서로의 화면이나 권한 있는 데이터를 합쳐 렌더링하지 않는다.

### 7.1 카테고리와 지도

- **FR-CAT-001** 시민 신고 카테고리는 `public_utility/수도·전기·가스`, `road_obstruction/도로 점유`, `streetlight_failure/가로등 고장`, `abandoned_vehicle/무번호판 방치 차량`, `road_sidewalk/노면 불량`, `bus_issue/버스 문제`, `traffic_safety/교통 표지·노면표시`, `other/기타` 8개로 고정한다.
- **FR-CAT-002** 도로 관련 분류는 점유, 노면 불량, 교통 표지·노면표시를 별도 카테고리로 보존한다.
- **FR-CAT-003** 공공 서비스 관련 분류는 수도·전기·가스, 가로등 고장과 버스 문제를 별도 카테고리로 보존한다.
- **FR-CAT-004** 무번호판 방치 차량과 기타 민원은 각각 별도 카테고리로 보존하며, 기존 `waste_pollution`과 `park_facility` 데이터는 조회 호환성을 유지한다.
- **FR-CAT-005** 시민과 관리자 지도는 카테고리별 이모지·모양과 텍스트를 함께 사용해 PIN을 구분한다.
- **FR-MAP-001** 시민은 타오위안 13개 행정구 중 하나와 해당 경계 안의 PIN 하나를 선택한다.
- **FR-MAP-002** 서버는 행정구 식별자, 좌표 형식·범위와 실제 행정구 경계 포함 여부를 다시 검증한다.
- **FR-MAP-003** 지역 QR에서 얻은 행정구는 접수 초안에 고정한다.
- **FR-MAP-004** GPS는 일반 신고에서 선택 사항이고 재발 현장 증빙에서 필수다.
- **FR-MAP-005** 초기 버전은 주소를 입력해 위치를 검색하는 기능과 사진 위 추가 PIN을 지원하지 않는다.
- **FR-MAP-006** 유효한 PIN 좌표가 바뀌면 서버가 역지오코딩한 주소를 좌표와 함께 표시하고, 최종 제출 시 서버가 같은 좌표로 주소를 다시 확인한다.
- **FR-MAP-006** 시민 또는 관리자가 행정구를 선택하면 지도는 해당 행정구 중심과 개별 위치를 선택할 수 있는 확대 수준으로 이동한다.
- **FR-MAP-007** 시민 접수 지도는 처음 열릴 때 권한을 받은 현재 위치를 중심으로 최대 확대하고, 시민 접수 지도와 관리자 지도는 현재 위치로 돌아오는 버튼과 서비스 범위 밖·권한 거부 안내를 제공한다.

타오위안 13개 행정구는 `桃園區`, `中壢區`, `平鎮區`, `八德區`, `楊梅區`, `大溪區`, `蘆竹區`, `大園區`, `龜山區`, `龍潭區`, `新屋區`, `觀音區`, `復興區`다.

### 7.2 입력·사진·인증

- **FR-IN-001** 제목, 본문, 카테고리, 행정구, 유효한 PIN과 서버가 확인한 주소, 사진 한 장과 확인된 이메일 세션이 있어야 제출할 수 있다.
- **FR-IN-002** 제목은 5~80자, 본문은 10~2,000자로 클라이언트와 서버에서 검증한다.
- **FR-IN-003** 시민에게 이메일, 본문, 사진과 AI 처리 목적을 제출 전에 안내한다.
- **FR-PH-001** 일반 신고와 재발 신고는 사진 정확히 한 장을 받으며 동영상은 지원하지 않는다.
- **FR-PH-002** 서버는 실제 이미지 형식, 10MiB와 25메가픽셀 한도를 확인하고 SVG를 거부한다.
- **FR-PH-003** 사진은 방향을 보정하고 메타데이터를 제거한 안전한 래스터 형식으로 재인코딩해 비공개 Storage에 저장한다.
- **FR-PH-004** 사진 또는 DB 저장이 실패하면 티켓을 접수로 표시하지 않고 연결되지 않은 임시 사진을 정리한다.
- **FR-PH-005** 재발 현장 증빙은 앱 내부 카메라로 새로 촬영하며 갤러리 파일을 증빙으로 인정하지 않는다.
- **FR-PH-006** 웹 환경에서 장면과 촬영 시점의 절대적 진위를 보장할 수 없음을 운영 정책에 명시하고, 위치·짧은 제출 시간·중복 제한·관리자 확인을 함께 사용한다.
- **FR-PH-007** 일반 신고는 기기의 기존 이미지 선택과 후면 카메라 즉시 촬영을 모두 제공하며 두 경로에 같은 서버 사진 검증을 적용한다.
- **FR-AUTH-001** 시민은 접수 시 이메일 OTP로, 내 티켓 조회 시 이메일 일회용 매직 링크로 인증한다.
- **FR-AUTH-002** 활성 관리자 멤버십, 이메일 OTP와 현재 세션의 개인 관리자 번호 확인 없이는 접근을 허용하지 않는다.
- **FR-AUTH-003** 관리자 번호와 OTP 시도에는 계정·IP 기준 속도 제한과 잠금 정책을 적용한다.

### 7.3 티켓 생성과 조회

- **FR-TK-001** 같은 idempotency key와 내용의 재시도는 티켓을 중복 생성하지 않는다.
- **FR-TK-002** 티켓, 사진 연결과 최초 `received` 이벤트가 정본 DB에 기록된 뒤에만 성공으로 응답한다.
- **FR-TK-003** 성공 화면은 사람이 읽을 수 있는 티켓 번호, 접수 시각과 인증이 필요한 조회 경로를 보여준다.
- **FR-TK-004** 작성자가 아닌 시민은 티켓 번호를 알아도 민원, 상태, 사진과 문제지점 연결을 조회할 수 없다.
- **FR-TK-005** 존재하지 않는 티켓과 다른 사람의 티켓은 구분되지 않는 오류로 응답한다.
- **FR-TK-006** 시민은 같은 이메일의 일회용 매직 링크로 자기 티켓을 조회한다.
- **FR-TK-007** 시민 메인 화면의 상태별 건수는 로그인한 사용자의 티켓만 센다.
- **FR-TK-008** 내 티켓 화면은 전체와 5개 행정 상태별 탭, 각 탭의 건수와 해당 티켓 목록을 제공한다.

### 7.4 행정 상태와 이력

- **FR-ST-001** `received`는 사진과 티켓 생성이 모두 성공한 경우에만 설정한다.
- **FR-ST-002** `viewed`는 권한 있는 관리자가 상세를 최초로 성공적으로 연 한 번만 설정한다.
- **FR-ST-003** `in_progress`는 명시적 처리 시작, 관리자가 시작한 저장된 AI 작업 또는 부서 전달 중 하나가 성공한 경우에만 설정한다.
- **FR-ST-004** `on_hold`는 보류 사유 10~1,000자와 미래의 다음 확인 예정일이 있어야 설정한다.
- **FR-ST-005** `on_hold`에서 복귀하면 `in_progress` 이벤트를 새로 추가하고 과거 보류 이력을 보존한다.
- **FR-ST-006** `completed`는 `in_progress` 상태에서 최종 답변과 관리자의 확인이 있을 때만 설정한다.
- **FR-ST-007** AI, 이메일 발송 성공과 단순 부서 추천은 `completed`를 설정할 수 없다.
- **FR-ST-008** 현재 상태 변경, append-only 이벤트와 완료 이메일 작업은 필요한 단위별 DB 트랜잭션으로 처리한다.
- **FR-ST-009** 시민 화면은 시민용 상태명, 최초 변경 시각, 보류 정보와 완료 답변을 시간순으로 보여준다.

### 7.5 현장 상태·재발·문제지점

- **FR-FD-001** 행정 상태와 문제지점 현장 상태는 별도 열과 별도 이벤트 이력으로 관리한다.
- **FR-FD-002** 행정 완료 시 처리 후 증빙이 없으면 현장 상태를 `verification_pending`으로 둔다.
- **FR-FD-003** 해결 확인에는 행위자, 증빙 사진, 확인 시각과 방법을 기록한다.
- **FR-FD-004** 재발 신고는 새 티켓 번호와 새 행정 이력을 가진다.
- **FR-RE-001** 재발 후보 검색과 연결은 서버 내부에서 실행하며 시민에게 다른 신고자의 과거 민원 식별자를 포함하지 않는다.
- **FR-RE-002** 검증된 재발은 과거 완료 티켓을 수정하지 않고 문제지점 현장 상태를 `recurrence_confirmed`로 바꾼다.
- **FR-RE-003** 재발 후보의 자동 또는 관리자 판정 이유와 행위자를 감사 이력에 남긴다.
- **FR-RE-004** 위치·카테고리 일치만으로 검증된 재발을 확정하지 않는다.
- **FR-RE-005** 재발 촬영 토큰은 로그인 사용자가 소유한 완료·현장 미해결 티켓에서만 요청할 수 있고, 현재 위치가 원본 PIN 반경 500m 안일 때만 발급한다.
- **FR-RE-006** 재발 신고는 `위치 승인 → 앱 카메라 촬영 → 제목·설명 입력 → 제출` 순서를 강제하며 서버는 새 티켓의 카테고리·행정구·PIN을 원본 티켓에서 정한다.
- **FR-SP-001** 최근 90일, 반경 30m, 서로 다른 시민 2명 이상, 검증된 재발 3건 이상이면 관리자용 시급 문제지점으로 표시한다.
- **FR-SP-002** 같은 사용자의 24시간 내 반복 신고는 시급성 집계에서 한 번만 센다.
- **FR-SP-003** 시급 문제지점은 지도·목록 정렬과 배지에 사용하지만 자동 상태 변경에 사용하지 않는다.
- **FR-SP-004** 같은 행정구·카테고리에서 반경 30m 안의 유효 민원 5건 이상을 일반 `문제지점`으로 표시하며, 개별 티켓과 행정 이력은 합치거나 삭제하지 않는다.
- **FR-SP-005** 일반 문제지점과 검증된 재발 기반 시급 문제지점은 별도 기준으로 계산하고 서로 다른 마커·건수·배지로 구분한다.

### 7.6 관리자 지도·하단 시트·목록

- **FR-AD-001** 관리자 첫 화면은 모든 개별 티켓 PIN과 문제지점을 표시하는 지도다.
- **FR-AD-002** 지도 상단에 다섯 행정 상태의 현재 건수를 표시한다.
- **FR-AD-003** 상태, 카테고리, 행정구, 위험도, 문제지점과 재발 여부로 PIN을 필터링한다.
- **FR-AD-004** PIN 선택 시 하단 시트에 티켓, 본문, 비공개 사진, 연락처, 주소와 정확한 좌표, 상태 이력, 담당 부서, 위험도와 재발 후보를 표시한다.
- **FR-AD-005** 하단 시트는 처리 시작, AI 작업, 부서 전달, 보류, 처리 재개, 위험도 수정, 재발 연결 확인, 처리 후 증빙과 완료를 제공한다.
- **FR-AD-006** 전체 목록은 지도와 같은 필터와 상세 컴포넌트를 사용한다.
- **FR-AD-007** 관리자 동작은 권한을 검증하는 서버 명령을 사용하고 브라우저가 테이블을 직접 수정하지 않는다.
- **FR-AD-008** 관리자 상세의 모든 읽기와 변경은 감사 로그를 남긴다.

### 7.7 AI 사전 필터·위험도·관리자 작업

- **FR-AI-001** 제목과 본문은 유해 내용, 광고·무관 내용, 반복, 개인정보 가능성을 이유 코드로 표시하는 사전 필터를 거친다.
- **FR-AI-002** 욕설, 분노 또는 강한 행정 비판만으로 티켓을 삭제·거부하지 않는다.
- **FR-AI-003** 사전 필터 장애 시 티켓을 보존하고 관리자 검토 대상으로 표시한다.
- **FR-AI-004** AI 위험도는 1~5단계, 이유 코드, 모델·버전과 판정 시각을 저장한다.
- **FR-AI-005** 관리자는 위험도를 수정할 수 있고 원래 AI 결과와 수정 이력을 모두 보존한다.
- **FR-AI-006** 관리자 AI 작업은 요약과 답변 초안으로 한정한다.
- **FR-AI-007** AI 작업이 재시도 가능한 작업으로 저장된 경우에만 행정 상태를 `in_progress`로 바꿀 수 있다.
- **FR-AI-008** AI 결과는 최종 상태, 현장 해결, 부서 전달과 공개 통계를 임의로 확정하지 않는다.
- **FR-AI-009** 실행되지 않은 AI 결과나 근거 없는 신뢰도를 표시하지 않는다.

### 7.8 집계형 공개 플레이어

- **FR-PL-001** 플레이어는 타오위안 13개 행정구를 설정된 순서로 자동 순환한다.
- **FR-PL-002** 축소 화면은 여러 행정구의 집계 클러스터를 동시에 표시한다.
- **FR-PL-003** 확대 화면은 개별 티켓이 아니라 카테고리별 밀도와 공개 가능한 익명 문제지점을 표시한다.
- **FR-PL-004** 공개 문제지점은 최근 90일, 검증된 관련 신고 5건 이상, 서로 다른 시민 3명 이상인 경우에만 표시한다.
- **FR-PL-005** 공개 문제지점 위치는 원본 좌표가 아니라 50~100m 격자 또는 승인된 도로·공원 구역으로 일반화한다.
- **FR-PL-006** 공개 문제지점에는 카테고리, 90일 집계 신고 수, 재발 수와 집계 현장 상태만 표시한다.
- **FR-PL-007** 제목, 본문, 사진, 티켓 번호, 신고자, 정확한 좌표, 개별 시각과 관리자 메모를 공개 응답에 포함하지 않는다.
- **FR-PL-008** 공개 데이터는 전용 집계 snapshot에서만 제공하며 원본 티켓 테이블이나 Realtime 채널을 공개하지 않는다.
- **FR-PL-009** 공개 snapshot은 최대 5분 간격으로 갱신하고 소수 집단 억제 규칙을 다시 적용한다.
- **FR-PL-010** 행정구별 퍼센트의 분모가 10보다 작으면 수치 대신 `집계 데이터 부족`을 표시한다.
- **FR-PL-011** 현재 행정구의 QR은 행정구가 고정된 신규 신고 화면으로 연결한다.
- **FR-PL-012** 자동 순환은 일시정지·재개할 수 있고 모든 정보는 키보드와 스크린리더로 탐색할 수 있다.

### 7.9 공개 지표 정의

- **FR-MT-001** 모든 공개 지표의 기본 기간은 snapshot 생성일 직전 90일이다.
- **FR-MT-002** 행정 처리율은 기간 중 접수된 유효 티켓 가운데 snapshot 시점에 `completed`인 티켓의 비율이다.
- **FR-MT-003** 현장 해결 확인율은 기간 중 `verification_pending`, `resolved_confirmed`, `recurrence_confirmed` 중 하나가 된 문제지점 가운데 snapshot 시점에 `resolved_confirmed`인 문제지점의 비율이다.
- **FR-MT-004** 보류 티켓은 행정 처리율 분모에 포함하고 완료 분자에는 포함하지 않는다.
- **FR-MT-005** 취소·테스트·중복으로 관리자 무효 판정을 받은 티켓은 공개 지표에서 제외하고 제외 사유를 내부 감사 이력에 남긴다.
- **FR-MT-006** 플레이어는 지표 이름, 기간, 분자·분모 건수와 마지막 갱신 시각을 함께 표시한다.

### 7.10 이메일 알림

- **FR-EM-001** 완료 이벤트와 완료 이메일 작업을 같은 DB 트랜잭션에 기록한다.
- **FR-EM-002** 보류 시 사유와 다음 확인 예정일 알림 작업을 생성한다.
- **FR-EM-003** 이메일에는 티켓 번호, 상태, 변경 시각과 인증이 필요한 조회 경로만 포함한다.
- **FR-EM-004** 이메일 실패가 행정 상태를 되돌리지 않으며 outbox에서 비동기로 재시도한다.
- **FR-EM-005** 상태 이벤트와 이메일 종류 조합은 한 번만 생성하고 전달 사업자의 idempotency key를 사용한다.
- **FR-EM-006** 관리자는 발송 대기·성공·실패를 확인하고 실패 작업을 다시 시도한다.

### 7.11 로컬라이제이션

- **FR-I18N-001** 시민 화면과 공개 플레이어는 `zh-TW`, `en`, `vi`를 지원하고 `zh-TW`를 기본값으로 사용한다.
- **FR-I18N-002** 언어 선택은 URL 또는 사용자 설정으로 유지하고 화면 전환 후에도 보존한다.
- **FR-I18N-003** 상태명, 카테고리, 오류, 이메일과 접근성 레이블을 번역 리소스에서 제공한다.
- **FR-I18N-004** 날짜·시간은 `Asia/Taipei` 기준으로 표시하고 선택 언어에 맞게 형식화한다.
- **FR-I18N-005** 시민이 작성한 제목·본문은 원문을 정본으로 저장한다.
- **FR-I18N-006** 자동 번역은 관리자 참고용 AI 결과로만 제공하며 원문을 덮어쓰지 않는다.
- **FR-I18N-007** 번역 누락 시 번체 중국어로 안전하게 대체하고 번역 키 자체를 사용자에게 표시하지 않는다.

## 8. 데이터와 권한 경계

### 8.1 정본 데이터

- **티켓:** 소유자, 카테고리, 행정구·정확한 좌표, 제목, 본문, 현재 행정 상태, 담당 부서와 생성 시각
- **행정 상태 이벤트:** 이전·새 상태, 원인, 행위자, 보류 정보, 최종 답변과 시각
- **비공개 연락처:** 검증된 이메일과 사용자 ID
- **비공개 사진:** 접수·재발·처리 후 증빙 구분, 저장 경로, 형식·크기와 검증 정보
- **문제지점:** 내부 대표 좌표, 카테고리, 현재 현장 상태와 재발 집계
- **티켓-문제지점 연결:** 후보·확정·해제 상태, 판정 이유와 행위자
- **현장 상태 이벤트:** 이전·새 상태, 증빙, 행위자, 시각과 방법
- **AI 결과:** 사전 필터, 위험도, 재발 후보, 모델·버전과 관리자 수정 이력
- **관리자 멤버십:** 개인 관리자 번호, 인증 사용자 ID와 활성 여부
- **알림 outbox:** 이메일 종류, 상태 이벤트, 시도 횟수, 잠금, 오류와 발송 시각
- **공개 집계 snapshot:** 행정구·기간·카테고리 집계, 두 해결 지표와 공개 가능한 일반화 문제지점

### 8.2 권한 원칙

- 시민은 자기 티켓과 연결 사진만 읽고 서버 접수 경로 외에는 원본 테이블을 수정하지 않는다.
- 시민은 다른 시민의 개별 티켓과 문제지점 연결을 조회하지 않는다.
- 관리자는 활성 멤버십, 이메일 OTP와 현재 세션의 관리자 번호 확인을 통과한 뒤 업무상 필요한 원본 데이터를 본다.
- 관리자 번호는 브라우저 저장소나 로그에 평문으로 보존하지 않는다.
- 사진은 비공개 Storage에 두고 영구 공개 URL을 만들지 않는다.
- 사진 응답은 매번 티켓 소유권 또는 관리자 권한을 확인하고 `private, no-store`로 제공한다.
- 공개 플레이어는 원본 테이블의 view를 직접 읽지 않고 최소 집계 기준을 통과한 별도 snapshot만 읽는다.
- 공개 snapshot 생성은 권한 있는 서버 작업만 수행하고 생성 입력·출력 건수를 감사한다.
- 노출 스키마의 모든 테이블은 RLS를 활성화하고 Data API 권한을 명시적으로 `GRANT/REVOKE`한다.
- `SECURITY DEFINER`가 필요한 함수는 비노출 스키마에 두고 호출자·인자를 함수 안에서 다시 검증한다.
- secret/service role 키는 브라우저에 제공하지 않는다.
- 인증 사용자를 삭제해도 티켓과 상태 이력이 연쇄 삭제되지 않도록 보존 정책을 사용한다.

## 9. 비기능 요구사항

### 9.1 보안·개인정보

- 모든 입력, 좌표, 이미지, 상태 전이, 위험도 수정과 재발 연결을 서버에서 검증한다.
- 시민 제출, 재발 증빙, 이메일 인증과 관리자 인증에 속도 제한을 적용한다.
- 서비스 로그에 이메일, 본문, 사진 경로, 토큰과 관리자 번호를 기록하지 않는다.
- 공개 snapshot은 소수 집단 억제와 좌표 일반화 검사를 통과하지 못하면 배포하지 않는다.
- 공개 API 응답 스키마에 개별 티켓 식별자나 원본 좌표 필드를 만들지 않는다.
- 개인정보 열람·정정·삭제 요청과 법적 보존 의무의 처리 절차를 외부 파일럿 전에 승인한다.
- 외부 공개 테스트 전 CAPTCHA, 세션 폐기와 관리자 접근 감사 조회를 적용한다.
- 공식 운영 전 대만 개인정보보호 및 정부 정보공개 관련 법률 검토를 완료한다.

### 9.2 일관성·실시간

- 정상 네트워크에서 시민 제출과 관리자 상태 변경은 5초 이내 권한 있는 열린 화면에 반영한다.
- Realtime은 변경 신호로만 사용하고 최신 권한 snapshot을 다시 조회한다.
- 공개 플레이어에는 원본 Realtime을 사용하지 않고 최대 5분 간격의 서버 집계 snapshot만 제공한다.
- 티켓 생성, 상태 이벤트, 재발 연결, 위험도 수정과 이메일 작업은 중복 요청에도 한 번만 반영한다.
- 네트워크 복구 후 누락된 상태를 다시 동기화한다.

### 9.3 성능

- 시민 주요 화면은 일반 4G 네트워크에서 핵심 조작이 가능한 상태를 3초 이내 제공하는 것을 목표로 한다.
- 지도는 현재 viewport와 필터에 필요한 PIN만 요청한다.
- 관리자 목록은 서버 페이지네이션을 사용한다.
- 위치 검색에는 행정구·카테고리·상태·좌표에 적합한 공간 및 복합 인덱스를 사용한다.
- 공개 플레이어는 사전 계산된 snapshot을 캐시하고 원본 티켓을 요청마다 집계하지 않는다.

### 9.4 접근성·기기

- 시민 접수와 재발 촬영은 실제 iOS Safari와 Android Chrome에서 검증한다.
- 관리자 지도·하단 시트·모달은 데스크톱과 태블릿에서 동작한다.
- 모든 핵심 조작은 키보드로 가능하고 모바일 터치 대상은 최소 44×44px다.
- 지도 정보는 접근 가능한 목록 또는 표로도 제공한다.
- 상태, 카테고리와 위험도는 색만으로 구분하지 않고 이름·아이콘·시각을 함께 표시한다.
- dialog는 초점 이동·가두기·복원과 Escape 닫기를 지원한다.
- 업로드, 제출, 상태 변경, 이메일, 카메라·위치 오류는 `aria-live`로 전달한다.
- 플레이어 자동 순환은 일시정지·재개하고 OS의 동작 줄이기 설정을 존중한다.

### 9.5 운영·복구

- 실제 시민 데이터 수집 전 DB와 비공개 Storage를 각각 백업하고 복원 시험을 통과한다.
- 이메일 outbox, AI 작업, 공개 snapshot 생성과 사진 정리 작업에 자동 재시도와 실패 경보를 둔다.
- 연결되지 않은 임시 사진은 안전한 유예시간 후 정리한다.
- 관리자 접근, 상태 변경, 위험도 수정, 재발 연결과 snapshot 생성의 감사 로그를 보존한다.
- 공식 운영 전 장애 공지, 연락 책임자와 복구 목표를 승인한다.

## 10. 검증 시나리오

### 10.1 시민 접수·소유권

- 필수 입력, 유효한 PIN, 사진 또는 검증된 이메일 세션 중 하나라도 빠지면 접수되지 않는다.
- 같은 idempotency key를 재전송해도 티켓·사진 연결·최초 이벤트는 하나만 생긴다.
- 사진 또는 DB 저장 실패 시 티켓 번호와 접수 상태가 표시되지 않는다.
- 다른 시민은 티켓 번호를 알아도 티켓, 상태 이력과 사진을 조회할 수 없다.
- 세 카테고리는 서로 다른 아이콘과 텍스트로 구분된다.
- `/`에는 시민 화면만, `/admin`에는 관리자 인증 또는 업무 화면만 표시된다.
- 행정구 선택 시 시민·관리자 지도의 중심과 확대 수준이 바뀐다.
- 현재 위치 권한 승인 시 지도에 현재 위치가 표시되고, 일반 신고는 이미지 선택과 즉시 촬영 입력을 모두 제공한다.

### 10.2 행정 상태

- 지도 PIN과 목록 노출은 `viewed`를 만들지 않는다.
- 상세를 최초로 성공적으로 열 때만 `received → viewed` 이벤트가 한 번 생긴다.
- 저장된 처리 시작·AI 작업·부서 전달 없이 `in_progress`로 갈 수 없다.
- 보류 사유와 다음 확인 예정일 없이 `on_hold`로 갈 수 없다.
- `on_hold`에서 바로 완료할 수 없다.
- 최종 답변과 관리자 확인 없이 `completed`가 될 수 없다.
- 완료와 이메일 작업 생성 사이에 부분 성공이 없다.

### 10.3 현장 상태와 재발

- 행정 완료만으로 현장 상태가 `resolved_confirmed`가 되지 않는다.
- 처리 후 증빙이 없으면 `verification_pending`으로 남는다.
- 재발 신고는 원본 티켓을 수정하지 않고 새 티켓을 만든다.
- 다른 시민의 과거 티켓 식별자와 내용은 재발 신고 응답에 포함되지 않는다.
- 위치만 가까운 다른 카테고리 티켓은 자동 재발로 확정되지 않는다.
- 카메라·5분·500m 조건을 충족하지 못한 일반 사진은 현장 증빙 가능으로 표시되지 않는다.
- 검증된 재발 3건과 시민 수 기준을 충족하면 관리자용 시급 문제지점이 표시된다.
- 같은 사용자의 24시간 반복 신고가 시급성 건수를 부풀리지 않는다.
- 같은 행정구·카테고리·반경 30m 안의 유효 민원 5건은 개별 티켓을 보존한 채 하나의 관리자용 문제지점으로 표시된다.
- 문제지점 필터, 지도 마커, 목록과 상세 화면의 연결 민원 수가 같은 값을 표시한다.

### 10.4 AI 위험도

- AI는 모든 신규 티켓에 위험도 또는 `평가 필요` 상태와 이유를 기록한다.
- 관리자는 위험도를 수정하고 변경 이유를 남길 수 있다.
- AI 실패 시 티켓이 삭제·거부·완료되지 않는다.
- AI 위험도와 재발 제안만으로 상태나 공개 snapshot이 변경되지 않는다.

### 10.5 관리자 화면

- 비관리자는 관리자 지도, 목록, 연락처와 사진을 조회할 수 없다.
- 관리자 번호만 입력해서는 로그인할 수 없다.
- 지도 상단 다섯 상태 건수와 필터 결과가 일치한다.
- 지도 하단 시트와 목록 모달은 같은 데이터와 명령 결과를 표시한다.
- 위험도순·재발순 정렬이 서버 페이지네이션에서도 안정적으로 유지된다.

### 10.6 공개 플레이어와 개인정보

- 공개 응답에 개별 티켓 ID, 티켓 번호, 제목, 본문, 사진, 신고자, 정확한 좌표와 개별 시각이 없다.
- 최근 90일 5건·시민 3명 기준을 충족하지 못한 문제지점은 공개되지 않는다.
- 공개 위치는 원본 좌표가 아닌 일반화 위치다.
- 분모가 10보다 작은 퍼센트는 `집계 데이터 부족`으로 표시된다.
- 행정 처리율과 현장 해결 확인율은 같은 값으로 합쳐지지 않는다.
- 공개 snapshot 갱신 전에는 새 민원이 노출되지 않으며 원본 티켓은 어떤 응답에도 포함되지 않는다.
- 13개 행정구 순환, 확대·축소, QR과 일시정지·재개가 동기화된다.

### 10.7 언어·접근성

- 번체 중국어, 영어, 베트남어에서 핵심 접수·상태·오류 문구가 빠지지 않는다.
- 선택 언어가 페이지 이동과 인증 후에도 유지된다.
- 시민 원문은 자동 번역으로 덮어쓰지 않는다.
- 지도와 플레이어의 동일 정보가 키보드로 접근 가능한 목록 또는 표에 존재한다.
- 하단 시트와 모달을 닫으면 초점이 원래 PIN 또는 목록 항목으로 돌아간다.

## 11. 출시 단계

일정 추정보다 위험이 큰 수직 흐름을 먼저 연결한다.

1. **환경 민원 핵심:** 세 카테고리, 13개 행정구 경계, 시민 접수, 이메일 OTP, 비공개 사진, 티켓 조회
2. **관리자 운영:** 관리자 번호+이메일 OTP, 지도, 하단 시트, 전체 목록, 다섯 행정 상태와 이메일
3. **현장 해결:** 문제지점, 현장 상태, 처리 후 증빙, 재발 후보·승인과 시급 문제지점
4. **AI 지원:** 사전 필터, 위험도 1~5, 요약·답변 초안과 관리자 수정 이력
5. **집계형 플레이어:** 공개 snapshot, 소수 집단 억제, 좌표 일반화, 13개 행정구 순환과 QR
6. **다국어·파일럿:** 번체 중국어·영어·베트남어, CAPTCHA, 운영 SMTP, 자동 작업, 백업·복원과 접근성 검증

각 단계는 실제 DB·Storage·이메일·AI 의존성과 검증 증거가 연결된 뒤 완료로 본다. 정적 데모 데이터만으로 단계를 완료 처리하지 않는다.

## 12. MVP 비목표

- 기존 타오위안 행정 시스템 연동
- 개별 민원 공개, 시민 간 티켓 열람과 공개 사진
- 시민이 다른 시민의 완료 티켓을 선택해 직접 재신고하는 기능
- 시민 댓글·채팅·공감·인기순과 행정 우선순위 투표
- 여러 사진, 동영상, 사진 위 추가 PIN과 이미지 편집
- 주소 검색과 GPS 자동 일반 신고
- 원본 음성 저장과 음성 전사 접수
- AI의 자동 거부·공개·부서 전달·보류·완료
- 완료 티켓의 재개와 과거 이벤트 수정
- 복잡한 조직도, 부서별 세분 권한, SLA와 자동 에스컬레이션
- 고급 분석·데이터 내보내기와 카테고리 관리 화면
- 정식 정부 서비스 브랜딩, 법정 보존기간과 고급 재해복구 보장

## 13. 후속 제품 방향

- 시민이 자기 완료 티켓의 현장 해결 여부를 사진으로 확인하는 전용 흐름
- 공인 현장 담당자 역할과 처리 후 증빙 표준화
- 민원 보완·정정·재검토와 사유 있는 완료 티켓 재개
- 자동 번역의 품질 평가와 관리자 승인 번역
- 사진 추가 첨부, 공개 가능한 행정기관 처리 증빙과 이미지 주석
- 관리자 역할 분리, 부서별 대기열과 SLA
- 타오위안 행정 시스템 연동과 공식 접수번호 매핑
- 법적 보존기간, 개인정보 영향평가, 운영 모니터링과 정식 접근성 인증

## 14. 출시 승인 기준

CivicPin 2.0은 다음이 모두 충족된 뒤 파일럿 준비 완료로 본다.

- 시민과 관리자가 다른 기기에서 신규 접수부터 완료 이메일까지 실제 데이터로 수행한다.
- 행정 완료 뒤 현장 상태가 자동 해결되지 않는 것이 DB 테스트로 증명된다.
- 새 재발 티켓이 과거 완료 티켓을 변경하지 않고 문제지점에 연결된다.
- 비관리자와 다른 시민이 원본 티켓·사진·문제지점 연결을 조회하지 못한다.
- 공개 플레이어 계약 테스트가 금지 필드 부재, 소수 집단 억제와 좌표 일반화를 증명한다.
- 관리자 번호 단독 접근이 거부되고 활성 멤버십·이메일 OTP·세션별 번호 확인이 적용된다.
- 실제 SMTP, AI 실패, snapshot 실패와 Storage 실패 복구 시나리오를 통과한다.
- DB·Storage 백업과 복원 시험을 통과한다.
- iOS Safari, Android Chrome, 데스크톱 키보드와 스크린리더 핵심 흐름을 검증한다.
- 대만 개인정보 및 공식 운영 관련 법률·정책 검토 결과를 반영한다.

## 15. 근거와 플랫폼 제약

- 타오위안시 정부 민정국의 공식 구청 목록을 13개 행정구 정본으로 사용한다: [타오위안시 각 구청 연락정보](https://cab.tycg.gov.tw/cp.aspx?Create=1&n=7929)
- 대만 개인정보보호법은 직·간접적으로 개인을 식별할 수 있는 정보를 개인정보로 정의하고 목적상 필요한 범위를 넘는 이용을 제한한다: [개인정보보호법](https://law.pdpc.gov.tw/LawContent.aspx?id=FL010627&kw=%E5%80%8B%E4%BA%BA%E8%B3%87%E6%96%99%E4%BF%9D%E8%AD%B7%E6%B3%95)
- 비식별화 절차를 거쳤더라도 재식별 가능성이 남으면 개인정보보호법 적용이 배제된다고 단정할 수 없다: [개인정보보호위원회 해석](https://www.pdpc.gov.tw/News_Content/102/360/)
- Supabase Data API 노출 권한과 RLS는 별도로 설계해야 한다: [Supabase Data API 보안](https://supabase.com/docs/guides/api/securing-your-api)
- 시민 사진은 public bucket이 아니라 접근 제어된 private bucket을 사용한다: [Supabase Storage 접근 모델](https://supabase.com/docs/guides/storage/buckets/fundamentals)
- 웹 카메라 촬영은 현재 세션에서 이미지를 얻는 수단이며 장면의 절대적 진위를 보장하는 공인 증명 수단은 아니다. CivicPin은 짧은 제출 시간, 위치, 중복 제한과 사람의 검토를 함께 사용한다.
