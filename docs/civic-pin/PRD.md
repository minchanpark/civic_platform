# CivicPin 제품 요구사항 문서

| 항목 | 내용 |
|---|---|
| 문서 상태 | Approved 1.0 — 핵심 흐름 우선 Fast MVP |
| 작성일 | 2026-08-14 |
| 현재 범위 | 실제 데이터로 연결되는 CivicPin MVP |
| 장기 방향 | 타오위안시 24시간 공식 민원 접수 서비스 |
| 데이터 정본 | CivicPin 자체 데이터베이스 |
| 기준 제품 | CivicMap의 시민·관리자 지도 UI + Pin Feedback의 QR·PIN·Realtime 패턴 |

## 1. 제품 요약

CivicPin은 시민이 카테고리를 선택하고 지도에 PIN을 찍어 민원을 제출한 뒤, 티켓 번호로 처리 현황을 확인하는 지도 기반 민원 플랫폼이다. 시민은 제목, 직접 입력한 본문 또는 음성 전사문, 사진 한 장을 제출한다. 관리자는 지도에서 PIN을 선택해 하단 시트로 내용을 열람하고, 처리 상태를 변경하며, 완료 시 시민에게 이메일을 보낸다.

현재 MVP는 CivicPin 자체 데이터베이스를 티켓의 정본으로 사용한다. 시민, 관리자, 공개 플레이어가 서로 다른 기기에서 같은 실제 데이터를 보고 상태 변경을 짧은 시간 안에 확인해야 한다. 로컬 저장소나 정적 데모 데이터로 성공을 흉내 내지 않는다.

장기적으로 공식 서비스 수준을 목표로 하지만, 이번 MVP를 정부의 공식 접수 채널로 표시하지 않는다. 법적 보존기간, SLA, 복잡한 부서 권한, 고급 재해복구 등은 외부 운영 전 별도 승인 대상으로 둔다.

## 2. 확정된 제품 결정

- **D-001** 장기 목표는 24시간 접수·조회가 가능한 공식 민원 서비스다.
- **D-002** CivicPin이 티켓 번호, 현재 상태와 상태 이력의 정본이다. 기존 행정 시스템 연동은 MVP에 없다.
- **D-003** 시민은 제출 전에 이메일 OTP를 확인한다. 검증된 사용자 ID가 티켓 소유권이며 티켓 번호나 이메일 링크 자체는 조회 권한이 아니다.
- 시민 업무 상태는 `received`, `viewed`, `in_progress`, `completed` 네 개만 사용한다.
- `viewed`는 권한 있는 관리자가 PIN의 상세 하단 시트를 처음 연 사실을 뜻한다.
- `in_progress`는 관리자가 처리를 시작하거나, 관리자가 시작한 AI 작업이 접수되거나, 다른 부서 전달이 저장된 경우를 뜻한다.
- `completed`는 관리자의 명시적 최종 확인으로만 설정한다. AI는 완료시킬 수 없다.
- 공개 여부는 업무 상태와 별도 필드로 관리한다.
- 사진은 한 장만 지원하고 시민과 관리자에게만 보여준다. 공개 플레이어에는 표시하지 않는다.
- 음성은 전사 후 시민이 확인한 텍스트만 저장하며 원본 음성은 저장하지 않는다.
- 공감·인기순·Top 5와 행사형 효과는 MVP 이후로 미룬다.

## 3. 목표와 성공 기준

### G-01. 끊김 없는 시민 접수

시민이 `카테고리 → 지도 확인 → PIN → 제목·본문·사진 → 제출 → 티켓 확인`을 모바일에서 완료할 수 있어야 한다.

### G-02. 이해 가능한 처리 현황

시민이 자기 티켓의 현재 상태, 상태별 변경 시각과 관리자의 완료 답변을 확인할 수 있어야 한다.

### G-03. 지도 중심 관리자 처리

관리자가 첫 화면의 지도에서 민원 위치와 상태를 파악하고, PIN 하단 시트 안에서 열람·처리·완료까지 수행할 수 있어야 한다.

### G-04. 실제 다기기 연결

시민 제출, 관리자 열람·상태 변경, 완료 이메일과 공개 플레이어 갱신이 실제 서버 데이터로 연결되어야 한다.

### G-05. 안전한 공개

장난성·악성·개인정보 포함 가능성을 사전에 표시하되 민원을 자동 삭제하지 않고, 관리자 승인 전에는 공개 플레이어에 노출하지 않아야 한다.

### 핵심 수직 흐름 완료 기준

다음 한 흐름이 서로 다른 시민 휴대전화와 관리자 PC에서 끝까지 동작하면 MVP의 핵심이 완료된다.

1. 시민이 민원을 제출하고 CivicPin 티켓 번호를 받는다.
2. 관리자가 지도 PIN을 열면 시민 화면이 `열람`으로 갱신된다.
3. 관리자가 처리 시작, AI 작업 시작 또는 부서 전달을 하면 `처리 중`으로 갱신된다.
4. 관리자가 완료 답변을 입력하고 최종 확인하면 `완료`로 갱신된다.
5. 완료 이메일이 발송되고, 시민이 이메일 인증이 필요한 티켓 화면에서 같은 결과를 확인한다.

제품 전체 요구는 이 흐름과 §10의 음성·필터·공개 플레이어 검증까지 포함한다. R-001에 따라 이 핵심 흐름을 `MVP 1차 완료`로 먼저 검증한다.

## 4. 사용자와 화면

### 시민

- 회원가입 화면 없이 민원을 작성할 수 있다.
- 회원가입 비밀번호 대신 이메일 OTP로 본인 이메일을 확인한다.
- 자기 티켓과 공개 승인된 민원만 볼 수 있다.
- 공개 지도 게시 여부는 시민이 직접 선택하며 기본값은 비공개다.
- 업무 상태나 공개 상태를 바꿀 수 없다.

### 관리자

- 인증되고 `staff_memberships`에 등록된 사용자만 관리자 화면에 접근한다.
- 지도와 하단 시트에서 민원을 열람하고 허용된 상태 전이를 실행한다.
- 공개 승인·비공개 유지, 부서 전달, AI 작업 시작과 완료 확인을 수행한다.
- 시민의 이메일과 비공개 사진을 볼 수 있으므로 모든 접근은 권한 검사를 거친다.

### 공개 플레이어 시청자

- 로그인 없이 공개 승인된 PIN과 공개용 본문만 본다.
- 시민 이메일, 사진, 티켓 번호, 내부 필터 결과와 관리자 메모는 볼 수 없다.

### 시민 메인 화면

- 고정 카테고리 카드
- `민원 접수` 진입 버튼
- `내 티켓 확인` 진입 버튼
- 전체 민원의 네 상태별 집계
- 공개 승인된 민원의 지도와 목록

### 관리자 메인 화면

- 전체 민원 PIN을 표시하는 지도
- 상태·카테고리 기본 필터
- PIN 선택 시 올라오는 상세 하단 시트
- 하단 시트 안의 열람 정보, 사진, AI·부서·상태 작업과 완료 답변

## 5. 핵심 사용자 여정

### J-01. 시민 민원 접수

1. 시민이 메인 화면에서 카테고리를 선택한다.
2. QR로 들어왔다면 QR의 지역을, 고정 URL로 들어왔다면 시민이 선택한 지역을 지도에 표시한다.
3. 시민이 지도에서 위치를 선택해 PIN 하나를 놓는다.
4. 텍스트·음성·사진을 받기 전에 개인정보와 음성 전사 처리 안내를 보여준다.
5. 시민이 제목을 입력한다.
6. 시민이 본문을 직접 입력하거나 음성을 녹음하고 전사문을 수정·확정한다.
7. 시민이 사진 한 장을 첨부한다.
8. 시민이 이메일 OTP를 확인한다.
9. 시민이 위치와 내용을 최종 검토하고 공개 지도 게시 여부를 선택한 뒤 제출한다.
10. 서버가 입력·사진·요청 빈도·중복 요청을 검증하고 티켓을 생성한다.
11. 시민에게 티켓 번호, `접수` 상태와 이메일 인증이 필요한 조회 경로를 보여준다.

### J-02. 시민 상태 확인

1. 시민이 같은 이메일 OTP 세션으로 `내 티켓`에서 인증이 필요한 티켓 화면을 연다.
2. 현재 상태와 각 상태의 변경 시각을 확인한다.
3. 완료된 경우 관리자의 최종 답변을 확인한다.
4. 공개에 동의했던 시민은 자기 티켓의 공개 동의를 철회할 수 있다.
5. 열린 화면은 상태 변경을 실시간으로 갱신하고, 연결 복구 후 다시 동기화한다.

### J-03. 관리자 처리

1. 관리자가 지도에서 PIN을 선택한다.
2. 서버가 하단 시트의 상세 데이터를 반환하고 최초 한 번만 상태를 `열람`으로 변경한다.
3. 관리자는 본문, 음성 입력 여부, 사진과 사전 필터 결과를 확인한다.
4. 관리자가 `처리 시작`, `AI 작업 시작` 또는 `부서 전달`을 실행하면 상태가 `처리 중`으로 변경된다.
5. 관리자가 최종 답변을 입력하고 완료 확인을 누르면 상태가 `완료`로 변경된다.
6. 완료 저장과 이메일 발송 작업이 함께 기록되고 시민 화면이 갱신된다.

### J-04. 지역 QR과 공개 플레이어

1. 플레이어가 현재 지역 지도와 같은 지역이 담긴 QR을 함께 표시한다.
2. 시민이 QR을 열면 그 지역이 접수 초안에 고정된다.
3. 관리자가 공개 승인한 새 민원이 생기면 플레이어가 해당 지역으로 이동해 PIN을 강조한다.
4. 현재 공개 상태인 모든 PIN은 지도에 누적된다.
5. 말풍선만 하나씩 순환하며, 모든 말풍선이 끝나면 처음부터 반복한다.

## 6. 기능 요구사항

### 6.1 카테고리와 지도

- **FR-CAT-001** MVP는 다음 다섯 카테고리를 고정값으로 제공한다: `도로 파손`, `가로등·공공시설`, `교통·안전`, `쓰레기·환경`, `기타`.
- **FR-CAT-002** 시민은 카테고리를 먼저 선택해야 지도 접수로 이동할 수 있다.
- **FR-MAP-001** 시민은 선택된 타오위안 지역 지도 안에 PIN 하나를 놓을 수 있어야 한다.
- **FR-MAP-002** 서버는 지역 식별자, 좌표 형식·범위와 지도 경계 안의 위치인지 다시 검증해야 한다.
- **FR-MAP-003** QR의 지역은 초안에 고정되며 플레이어가 다른 지역으로 넘어가도 바뀌면 안 된다.
- **FR-MAP-004** GPS 자동 위치, 주소 검색과 사진 위 추가 PIN은 MVP에 포함하지 않는다.

### 6.2 제목·본문·음성·사진

- **FR-IN-001** 제목, 최종 본문, 카테고리, 위치, 사진 한 장과 검증된 이메일 세션이 있어야 제출할 수 있다.
- **FR-IN-002** 제목은 5~80자, 최종 본문은 10~2,000자로 서버에서도 검증한다.
- **FR-IN-003** 본문은 직접 입력하거나 음성 전사로 작성할 수 있으며 두 경로는 같은 최종 검증을 사용한다.
- **FR-VO-001** 녹음은 최대 60초이며 시작, 중지, 재생, 삭제와 재녹음을 제공한다.
- **FR-VO-002** 전사문은 시민이 수정·확정하기 전에는 제출할 수 없다.
- **FR-VO-003** 원본 음성은 전사 성공·취소·오류 후 저장하지 않고 임시 파일과 Blob URL을 정리한다.
- **FR-VO-004** 녹음 미지원, 권한 거부 또는 전사 실패 시 작성 중인 내용을 잃지 않고 텍스트 입력으로 전환할 수 있어야 한다.
- **FR-PH-001** MVP는 사진 정확히 한 장을 받으며 여러 장과 동영상은 지원하지 않는다.
- **FR-PH-002** 서버는 실제 이미지 형식, 10 MiB 용량과 25메가픽셀 한도를 검증하고 SVG를 거부해야 한다. 지원 이미지는 방향을 보정하고 메타데이터를 제거해 안전한 래스터 형식으로 다시 인코딩한 비공개 파일만 저장한다.
- **FR-PH-003** 사진 업로드나 티켓 저장 중 하나라도 실패하면 티켓을 `접수`로 표시하지 않고 재시도할 수 있어야 하며, 티켓에 연결되지 않은 임시 사진을 정리해야 한다.
- **FR-PH-004** 사진은 작성자와 관리자만 볼 수 있고 공개 API, 플레이어와 이메일에는 포함하지 않는다.

### 6.3 티켓 생성과 조회

- **FR-TK-001** 서버는 제출 재시도에 같은 idempotency key를 사용해 중복 티켓을 만들지 않아야 한다.
- **FR-TK-002** 티켓과 최초 `received` 이벤트가 정본 DB에 기록된 뒤에만 성공으로 응답해야 한다.
- **FR-TK-003** 성공 화면은 사람이 읽을 수 있는 CivicPin 티켓 번호, 접수 시각과 인증이 필요한 조회 경로를 보여줘야 한다.
- **FR-TK-004** 티켓 번호는 비밀값으로 사용하지 않고 공개 화면에 노출하지 않아야 한다.
- **FR-TK-005** 티켓의 불변 소유자는 제출 당시 검증된 사용자 ID이며, 작성자가 아닌 시민은 티켓 번호를 알아도 상세 내용과 상태 이력을 조회할 수 없어야 한다.
- **FR-TK-006** 잘못된 티켓, 다른 작성자의 티켓과 존재하지 않는 티켓 조회는 정보를 구분해 노출하지 않아야 한다.
- **FR-TK-007** 시민은 다른 기기에서도 같은 이메일 OTP로 인증해 자기 티켓을 다시 찾을 수 있어야 한다.

### 6.4 업무 상태와 이력

```text
received → viewed → in_progress → completed
```

- **FR-ST-001** `received/접수`는 사진과 티켓 생성이 모두 성공한 경우에만 설정한다.
- **FR-ST-002** `viewed/열람`은 현재 상태가 `received`일 때 권한 있는 관리자가 PIN의 상세 하단 시트를 성공적으로 연 최초 한 번만 설정한다.
- **FR-ST-003** 지도 PIN 렌더링, 목록 노출, hover, 링크 미리읽기와 브라우저 prefetch는 `viewed`가 아니다.
- **FR-ST-004** `viewed` 처리는 원자적이고 멱등해야 하며 여러 관리자가 열어도 최초 시각을 덮어쓰지 않는다.
- **FR-ST-005** `in_progress/처리 중`은 현재 상태가 `viewed`이고 관리자의 명시적 처리 시작, 관리자가 시작한 실제 AI 작업의 접수, 또는 부서 전달 저장이 성공한 경우에만 설정한다.
- **FR-ST-006** 접수 전사·악성 내용 필터 실행은 `in_progress`로 보지 않는다.
- **FR-ST-007** `completed/완료`는 현재 상태가 `in_progress`이고 관리자가 최종 답변을 입력한 뒤 확인 동작을 완료한 경우에만 설정한다.
- **FR-ST-008** AI, 이메일 발송 결과와 단순 부서 추천은 `completed`를 설정할 수 없다.
- **FR-ST-009** 현재 상태 갱신과 append-only 상태 이벤트 추가는 한 DB 트랜잭션으로 처리하며, 완료 답변은 `completed` 이벤트에 함께 기록한다.
- **FR-ST-010** 시민 상태 화면은 상태명, 최초 변경 시각과 완료 답변을 시간순으로 보여준다.

### 6.5 관리자 지도와 하단 시트

- **FR-AD-001** 관리자 첫 화면은 모든 티켓 PIN이 표시된 지도여야 한다.
- **FR-AD-002** 관리자는 상태와 카테고리로 PIN을 필터링할 수 있어야 한다.
- **FR-AD-003** PIN 선택 시 하단 시트에 티켓 번호, 카테고리, 제목, 본문, 사진, 현재 상태, 시각, 담당 부서와 필터 결과를 표시해야 한다.
- **FR-AD-004** 하단 시트는 `처리 시작`, `AI 작업 시작`, `부서 전달`, `공개 승인·비공개`, `완료` 동작을 제공해야 한다.
- **FR-AD-005** 카테고리와 부서는 고정 데이터로 시작하며 관리 CRUD는 만들지 않는다.
- **FR-AD-006** 관리자 동작은 브라우저가 테이블을 직접 수정하지 않고 권한을 검증하는 서버 명령을 통해야 한다.
- **FR-AD-007** 어떤 OAuth 사용자도 자동으로 관리자가 되면 안 되며 명시적인 관리자 멤버십이 필요하다.

### 6.6 AI 사전 필터와 관리자 AI 작업

- **FR-AI-001** 제목, 직접 입력 본문과 시민이 확정한 전사문은 같은 서버 필터를 거쳐야 한다.
- **FR-AI-002** 필터는 유해 내용, 광고·무관 내용, 무의미한 반복과 개인정보 가능성을 이유 코드로 표시해야 한다.
- **FR-AI-003** 욕설, 분노 또는 강한 행정 비판만으로 티켓을 자동 삭제·거부하면 안 된다.
- **FR-AI-004** 필터 장애 시 티켓은 보존해야 한다. 공개 동의 티켓은 `pending_publication`, 미동의 티켓은 `private`으로 유지한다.
- **FR-AI-005** 사진은 공개하지 않고 관리자 하단 시트에서 수동 검토해야 한다. MVP의 AI 필터는 사진을 판정하지 않는다.
- **FR-AI-006** 관리자용 AI 작업은 민원 요약과 답변 초안 제안으로 한정한다.
- **FR-AI-007** 관리자가 AI 작업을 시작하고 내부의 재시도 가능한 작업이 저장된 경우에만 업무 상태를 `in_progress`로 바꾼다.
- **FR-AI-008** AI 제안은 관리자의 부서 전달이나 완료 확인을 대신할 수 없다.
- **FR-AI-009** 관리자 화면에 가짜 신뢰도나 실행되지 않은 AI 결과를 표시하면 안 된다.

### 6.7 공개 상태와 플레이어

```text
private → pending_publication → public
                         ↘ private
public → private
```

- **FR-PUB-001** 공개 선택 기본값은 `false`이며, 미동의 티켓은 `private`으로 생성한다.
- **FR-PUB-002** 시민이 공개를 명시적으로 선택한 티켓만 `pending_publication`으로 생성한다.
- **FR-PUB-003** 시민 동의, 개인정보를 가린 공개용 제목·본문과 안전한 좌표, 관리자 승인을 모두 충족해야 `public`으로 전이할 수 있다.
- **FR-PUB-004** 관리자 승인 전에는 제목, 본문, 좌표와 사진을 공개 API나 플레이어에 노출하면 안 된다.
- **FR-PUB-005** 시민이 자기 티켓에서 공개 동의를 철회하면 정본 티켓은 유지하고 공개용 데이터만 즉시 비활성화해야 한다.
- **FR-PUB-006** 시민 메인 화면은 전체 티켓의 네 업무 상태별 비식별 집계와 공개 승인된 민원만 보여준다.
- **FR-PL-001** 플레이어는 구성된 지역 지도를 자동 순환해야 한다.
- **FR-PL-002** 지역 전환 시 지도와 같은 지역 식별자가 담긴 QR을 함께 갱신해야 한다.
- **FR-PL-003** 승인된 새 공개 민원이 도착하면 해당 지역으로 이동해 PIN을 강조한 뒤 기존 자동 순환을 재개해야 한다.
- **FR-PL-004** 현재 `public`인 모든 PIN은 지도에 누적하고 재생 중 사라지지 않아야 한다.
- **FR-PL-005** 말풍선만 충돌을 피하며 하나씩 순환하고, 모든 말풍선을 재생하면 처음부터 반복한다.
- **FR-PL-006** 공개 클라이언트는 시민 이메일, 사진 경로, 티켓 번호와 내부 필터 결과를 받아서는 안 된다.

### 6.8 이메일 알림

- **FR-EM-001** 완료 상태 저장과 완료 이메일 작업 생성을 같은 DB 트랜잭션에 기록한다.
- **FR-EM-002** 완료 이메일은 티켓 번호, 완료 사실·시각과 이메일 인증이 필요한 조회 경로만 포함하고, 제목·본문·사진·정밀 위치와 최종 답변은 인증된 티켓 화면에서 보여준다.
- **FR-EM-003** 이메일 발송 실패가 티켓 상태를 되돌리면 안 되며 비동기로 재시도해야 한다.
- **FR-EM-004** 관리자는 발송 대기·성공·실패를 확인하고 실패 작업을 다시 시도할 수 있어야 한다.
- **FR-EM-005** 상태 이벤트와 이메일 종류의 조합은 한 번만 작업으로 생성하고, 전달 사업자의 idempotency key로 안전하게 재시도해야 한다.
- **FR-EM-006** 외부 시민 테스트 전 이메일 OTP와 완료 알림을 실제 수신할 수 있는 트랜잭션 이메일 발송 구성을 사용해야 한다.

## 7. 데이터와 권한 경계

### 정본 데이터

- 티켓: 카테고리, 지역·좌표, 제목, 확정 본문, 현재 상태, 공개 상태와 담당 부서
- 상태 이벤트: 이전 상태, 새 상태, 원인, 행위자, 시각과 완료 이벤트의 최종 답변
- 비공개 연락처: 검증된 이메일과 작성자 식별자
- 비공개 사진: 티켓과 연결된 저장 경로·형식·크기
- AI 결과: 필터 이유 코드, 관리자 작업 상태와 제안 결과
- 알림 작업: 이메일 종류, 상태, 시도 횟수와 마지막 오류
- 관리자 멤버십

### 권한 원칙

- 시민은 서버 접수 경로만 사용하고 티켓·상태·공개 여부를 직접 수정할 수 없다.
- 시민은 자기 티켓과 사진만 조회할 수 있다.
- 관리자는 멤버십과 서버 권한 검사를 통과한 뒤에만 전체 민원과 사진을 볼 수 있다.
- 사진은 비공개 Storage에 두고 영구 공개 URL을 만들지 않는다.
- 사진 조회 권한은 Storage 경로나 객체 소유자가 아니라 연결된 티켓의 작성자 ID 또는 활성 관리자 멤버십으로 매번 확인하고 응답을 캐시하지 않는다.
- 공개 조회는 공개 승인된 필드만 반환하는 전용 API 또는 RPC를 사용한다.
- Supabase migration은 모든 노출 테이블의 RLS와 필요한 Data API `GRANT/REVOKE`를 각각 명시해야 한다.
- secret/service role 키는 브라우저에 제공하지 않는다.
- service role을 쓰는 서버 경로는 DB·Storage RLS 우회를 전제로 애플리케이션 소유권을 다시 검증해야 한다.
- 인증 사용자 삭제가 CivicPin 티켓과 상태 이력을 연쇄 삭제하면 안 된다.

## 8. 비기능 요구사항

### 보안·개인정보

- 모든 입력, 좌표, 이미지와 상태 전이는 서버에서 다시 검증한다.
- 시민 제출과 티켓 조회에 속도 제한을 적용한다.
- 시민에게 이메일, 사진, 음성 전사와 AI 처리 목적을 제출 전에 알린다.
- 민감 응답은 `private, no-store`로 제공한다.
- 관리자와 시민의 개인정보 접근은 필요한 범위로 제한한다.
- 외부 공개 테스트 전 CAPTCHA와 관리자 다중 인증을 적용한다.

### 일관성·실시간

- 정상 네트워크에서 시민 제출과 관리자 상태 변경은 5초 이내 관련 열린 화면에 반영되어야 한다.
- Realtime 이벤트는 변경 신호로 사용하고 권한에 맞는 최신 snapshot을 다시 조회한다.
- 공개 Realtime은 원본 티켓·연락처·사진 행을 구독하지 않고 정제된 공개 변경 신호만 전달한다.
- 네트워크 재연결 후 누락된 상태를 다시 동기화한다.
- 티켓 생성, 상태 이벤트와 이메일 작업은 중복 요청에도 한 번만 반영되어야 한다.
- 실제 외부 시민 데이터를 받기 전에 DB와 비공개 사진을 각각 백업하고 한 번 이상 복원 확인을 해야 한다.

### 접근성·기기

- 시민 접수는 실제 iOS Safari와 Android Chrome에서 동작해야 한다.
- 관리자 지도와 하단 시트는 데스크톱과 태블릿에서 사용할 수 있어야 한다.
- 모든 핵심 조작은 키보드로 가능하고 모바일 터치 대상은 최소 44×44px이어야 한다.
- 지도 정보는 접근 가능한 목록으로도 제공한다.
- 상태는 색만으로 구분하지 않고 이름·시각과 함께 표시한다.
- 녹음, 업로드, 제출, 이메일과 상태 변경 결과는 화면 메시지와 `aria-live`로 전달한다.
- 플레이어 자동 순환은 일시정지·재개할 수 있어야 한다.

## 10. 검증 시나리오

### 시민 접수

- 카테고리, 유효한 PIN, 제목, 본문, 사진과 검증된 이메일 세션 중 하나라도 빠지면 제출되지 않는다.
- 음성 전사문을 시민이 확정하지 않으면 제출되지 않는다.
- 녹음 권한 거부나 전사 실패 후에도 이미 작성한 입력은 남고 텍스트로 제출을 계속할 수 있다.
- 전사가 끝나거나 취소·실패하면 서버 임시 음성과 브라우저 Blob URL이 남지 않는다.
- 사진 저장 또는 DB 저장 실패 시 티켓 번호와 `접수` 상태가 표시되지 않는다.
- 같은 idempotency key를 재전송해도 티켓은 하나만 생긴다.
- 성공 시 티켓과 `received` 이벤트가 생성되고 이메일 인증이 필요한 조회 화면으로 이동한다.

### 관리자 처리

- 비관리자는 관리자 지도와 사진을 조회할 수 없다.
- 지도 PIN이나 미리읽기는 상태를 바꾸지 않는다.
- 하단 시트를 처음 열 때만 `received → viewed` 이벤트가 한 번 생긴다.
- 관리자 처리 시작, 관리자 시작 AI 작업 접수 또는 부서 전달 성공만 `in_progress`를 만든다.
- 관리자 최종 답변과 확인 없이는 `completed`가 되지 않는다.
- 완료 저장과 이메일 작업 생성 사이에 부분 성공이 없어야 한다.
- AI 필터 장애나 유해 가능성 표시는 티켓을 삭제하거나 업무 상태를 `처리 중`·`완료`로 바꾸지 않는다.

### 시민 확인·공개

- 다른 시민은 티켓 번호를 알아도 상세를 볼 수 없다.
- 관리자의 상태 변경이 시민 티켓 화면에 반영된다.
- 이메일 실패 시 완료 상태는 유지되고 알림만 재시도된다.
- `pending_publication` 또는 `private` 티켓은 공개 응답과 플레이어에 나타나지 않는다.
- 시민이 공개에 명시적으로 동의하지 않으면 티켓은 `private`이고, 동의했어도 관리자 승인 전에는 `pending_publication`이다.
- 공개 플레이어는 승인된 모든 PIN을 누적하고 모든 말풍선을 반복한다.
- QR로 접수 화면을 연 뒤 플레이어 지역이 바뀌어도 시민의 접수 지역은 바뀌지 않는다.
- 새 공개 PIN을 강조한 뒤에는 중단했던 지역 자동 순환으로 복귀한다.

## 11. 구현 순서

일정 추정 없이 위험이 가장 큰 단일 흐름부터 연결한다.

1. **기반:** 독립 저장소·Supabase, 고정 카테고리·부서, 관리자 멤버십, 티켓·이벤트·비공개 사진
2. **시민 수직 흐름:** 카테고리, 지도 PIN, 제목·본문·사진, 이메일 OTP, 티켓과 상태 조회
3. **관리자 수직 흐름:** 지도, 하단 시트, `received → viewed → in_progress → completed`
4. **완료 알림:** 완료 이메일과 재시도
5. **음성·AI:** 녹음·전사문 확인, 사전 필터, 관리자 시작 AI 작업
6. **공개 화면:** 수동 공개 승인, 시민 현황, 지역 QR와 누적 플레이어

각 단계는 정적 데모가 아니라 실제 DB·Storage·이메일 또는 AI 의존성과 연결한 뒤 다음 단계로 넘어간다.

## 12. 후속 제품 방향

- 공감과 인기순은 공개 가시성에만 사용하고 행정 처리 우선순위에는 사용하지 않는다.
- 사진 추가 첨부, 공개 사진과 이미지 주석
- 시민 보완·정정·재검토와 더 세분화된 업무 상태
- 잘못 완료한 티켓의 사유 있는 재개와 정정 알림
- 관리자 역할 분리, 부서별 대기열과 SLA
- 저위험 공개 요청의 자동 승인 평가
- 타오위안 13개 지역 전체 운영과 공식 서비스 보안·개인정보·기록관리 승인
- 백업 복원 훈련, 장애 공지, 운영 모니터링과 정식 접근성 인증

## 13. 승인된 출시 경계

### R-001. MVP 출시 경계

제품 요구는 모두 이 문서에 유지하되 첫 검증 완료 지점은 핵심 흐름으로 확정한다.

| 접근 | 영향 |
|---|---|
| A. 전체 기능을 한 MVP로 승인 | 시민 핵심 흐름, 음성·AI, 수동 공개, QR·플레이어까지 §10을 모두 통과한 뒤 MVP 완료로 본다. 한 번에 제품 형태를 검증하지만 핵심 상태 흐름의 피드백이 늦어진다. |
| **B. 핵심 흐름을 MVP 1차 완료로 승인 — 선택됨** | §11의 1~4단계가 실제 의존성과 연결되면 먼저 검증하고, 음성·AI·공개 플레이어는 같은 PRD의 다음 MVP 증분으로 이어간다. 기능을 삭제하지 않으면서 시민→관리자→시민 상태 흐름을 먼저 확인할 수 있다. |

R-001은 2026-08-14에 B안으로 승인되었다. 프로젝트를 독립 저장소와 독립 Supabase로 분리하고 §11 순서대로 개발한다.

## 14. 근거와 현재 플랫폼 제약

- Supabase 신규 테이블은 Data API에 자동 노출되지 않을 수 있으므로 RLS와 API 권한을 별도로 설계한다: [Supabase Data API 변경](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)
- 사진은 public bucket이 아니라 접근 제어된 private bucket을 사용한다: [Supabase Storage access model](https://supabase.com/docs/guides/storage/buckets/fundamentals)
- 브라우저별 지원 녹음 형식은 런타임에 확인한다: [MDN `MediaRecorder.isTypeSupported`](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static)
- 완료된 녹음은 서버 파일 전사 방식으로 처리한다: [OpenAI File transcription](https://developers.openai.com/api/docs/guides/speech-to-text)
- 타오위안 공식 서비스 전환 시 개인정보 확인과 접수 절차를 다시 검토한다: [타오위안시 민원 FAQ](https://www.tycg.gov.tw/News_Content.aspx?n=97&s=1552505)
